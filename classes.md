# classes.md

Лабораторная работа № 6. Диаграмма классов. Сервис бронирования учебных аудиторий.

## Задание 1. Выделение классов

### Кандидаты в классы

| Кандидат | Что хранит | Что делает | Класс? (да/нет) |
| --- | --- | --- | --- |
| Аудитория | Номер, вместимость, здание | Сама отвечает, свободна ли она на нужный интервал | Да |
| Бронь | Начало, конец, цель, номер | Проверяет, пересекается ли с другой бронью; отменяется | Да |
| Сотрудник | ФИО, роль (староста или преподаватель), почту | Получает уведомление | Да |
| Дата | Просто значение: день, месяц, год | Ничего | Нет: атрибут Брони |
| Интервал времени | Только значение временного интервала | Ничего | Нет: атрибут Брони |
| Цель брони | Только текст с целью бронирования | Ничего | Нет: атрибут Брони |
| Расписание | Занятость аудиторий по датам | Отдаёт, какие аудитории заняты в нужный день | Да |
| Уведомление | Текст сообщения | Само ничего, его отправляют | Нет: результат операции отправки |
| Список свободных аудиторий | Результат поиска свободных аудиторий | Ничего | Нет: результат операции |
| Подтверждение | Результат подтверждения бронирования | Ничего | Нет: результат операции |

### Почему шесть строк не стали классами

* **Дата и Интервал времени.** Они ни за что не отвечают и ничего не умеют, это просто значения. Они нужны, но как параметры операций. Внутри Брони они превращаются в два атрибута: начало и конец.
* **Цель брони.** Это одна строка текста. Своих свойств и поведения у неё нет, значит это атрибут Брони.
* **Список свободных аудиторий и Подтверждение.** Это то, что система показывает в ответ. Нигде не хранится и само ничего не делает, поэтому это результат операции, а не класс.
* **Уведомление.** Выглядит как класс, но в сценарии его только отправляют, и дальше о нём никто не вспоминает. Текст можно собрать из данных Брони, а отправкой занимается отдельный исполнитель. Поэтому Уведомление оставлено результатом действия.

### Сущность, которой нет в сценарии явно

На шаге 5а сценария система должна проверить, не пересекается ли новая бронь с уже существующей. Для этого в классе Бронь (Booking) предусмотрен метод overlapsWith(other: Booking): bool, который проверяет пересечение временных интервалов двух броней.

**Итоговый список:** Аудитория, Бронь, Сотрудник, Расписание.

### Атрибуты и операции

| Класс | Атрибуты | Операции |
| --- | --- | --- |
| Аудитория | number, capacity, building | isAvailable(interval): bool |
| Бронь | id, startTime, endTime, purpose | overlapsWith(other: Booking): bool; cancel(): void |
| Сотрудник | id, name, email | hasActiveBooking(): bool |
| Расписание | occupiedSlots, lastUpdated | getOccupancy(date): List; refresh(): void |

## Задание 2. Связи и кратность

| Связь | Может ли быть ноль? | Может ли быть несколько? | Кратность |
| --- | --- | --- | --- |
| Аудитория → Бронь | Да, у новой аудитории броней нет | Да | 0..* |
| Бронь → Аудитория | Нет, бронь всегда для аудитории | Нет, ровно 1 | 1 |

| Проверка | Что должно быть | Выполнено? |

## Задание 3. Особые виды связей

### Композиция

Не используется. Ни один из классов не зависит от другого настолько, чтобы терять смысл при его удалении. Например, аудитория может существовать без брони.

### Агрегация

Здание и Аудитория (1 и 1..*). Аудитория может существовать независимо от здания и быть привязана к другому корпусу. Поэтому используется агрегация, а не композиция.

### Наследование

Не используется. Староста и преподаватель отличаются от других сотрудников только своей ролью, поэтому создавать для них отдельные классы не требуется. При необходимости достаточно добавить атрибут role в класс Сотрудник.
